# Development notes

Zelda on PC is [Cemu](https://github.com/cemu-project/Cemu) plus one extra library, `src/pcedition`, and a small
number of hooks in the emulator. This page says where things are and how to work on them.

## Layout

| Path | What |
|---|---|
| `src/pcedition/` | The PC layer (see the table below). Everything in the `pce` namespace. |
| `src/` (rest) | Cemu. Changes are small and marked with a `Zelda on PC` or `PC Edition` comment. |
| `src/Cafe/HW/Latte/Renderer/Vulkan/VulkanFFX.*`, `VulkanFSR.*` | AMD FSR 3 frame generation in the Vulkan renderer. |
| `bin/` | Run directory of a build: executable, `resources`, `gameProfiles`; `data` and `settings.ini` appear at run time. |
| `tools/` | Build, packaging, asset generation. `tools/dev/` holds the developer tools. |
| `installer/` | Inno Setup script of the Windows installer. |
| `dependencies/FidelityFX-SDK` | Submodule: FidelityFX API headers and the prebuilt, signed `amd_fidelityfx_vk.dll`. |

### `src/pcedition`

| File | Role |
|---|---|
| `PCEdition` | Startup: command line, paths, finding the game dump (title folders, `.wua`, `.wud` / `.wux` disc images) and reading files from it, forcing Cemu's configuration, save import. |
| `PCSettings` | `settings.ini`, key bindings. |
| `PCInput` | Raw Input thread; serves the game's `VPADRead` directly; camera, motion (tilt) and context logic. |
| `PCCamera` | Mouse to stick conversion for the camera modes without a direct hook. |
| `PCUI` | Live model of the game's interface: walks the layouts the game draws (screens, panes, texts). |
| `PCMenus` | Mouse pointer in the game's menus, map dragging, save / load macros. |
| `PCPrompts` | Key and mouse prompt glyphs in place of the GamePad buttons. |
| `PCGraphics` | Graphics options on top of the community graphic packs; generates the game patches. |
| `PCOverlay` | The in-game settings menu (Dear ImGui). |
| `PCIcon` | Window and shortcut icon, made on the player's machine from the icon of their dump. |
| `PCDevBridge`, `PCProfiler` | Developer mode only. |

## How the game is modified

Nothing is changed on disk. At every start `PCGraphics.cpp` writes a private graphic pack into the data folder
(`data/graphicPacks/BotWPCEdition`) and Cemu applies it like any other pack:

- **Code patches** (`patch_PCCamera.asm`): PowerPC assembly for the executable of update 1.5.0 (Cemu module checksum
  `0x6267BFD0`, identical in all regions). The patches are short trampolines that call functions of the emulator,
  registered with `osLib_addFunction("coreinit", "PCE_...")`. Each hook is commented with the address it replaces and
  what the surrounding game code does.
- **The prompt font**: the game's font archive is read from the player's own dump, its button glyph font is swapped
  for `resources/pcedition/External_00.bffnt`, and the result is placed in the pack's content folder on the player's
  machine. The glyphs are generated by `tools/make_prompt_font.py`; no game artwork is involved.

The community packs *Graphics* and *FPS++* are used unmodified; the settings menu selects their presets.
`tools/get_graphic_packs.ps1` fetches the release they were tested with (pinned by version and SHA-256).

Addresses, structure offsets and how they were found are documented next to the code that uses them. They are valid
for update 1.5.0 only, which is why the game refuses to start with any other version.

## Building

```bat
tools\build.cmd                 :: configure + build (release)
tools\build.cmd build release   :: build only
```

Output: `bin\ZeldaOnPC_release.exe`. It runs from `bin` once `bin\settings.ini` names the game folder
(`[Game]` / `Path=`), or when an existing Cemu installation already knows it.

```bat
powershell -ExecutionPolicy Bypass -File tools\package.ps1 -Version 1.3.6
```

stages the files in `build\stage` and builds `installer\output\ZeldaOnPC-Setup-1.3.6.exe`. Silent installation for
tests: `ZeldaOnPC-Setup-1.3.6.exe /VERYSILENT /GAMEDIR="D:\Games\BotW" /DIR="D:\Test"`.

Regenerating the art (Python 3 with Pillow and NumPy):

```bat
python tools\make_prompt_font.py bin\resources\pcedition\External_00.bffnt
python tools\make_app_icon.py
```

`make_app_icon.py` draws the icon that is built into the executable. It is only the fallback: the installed game
shows the icon of the player's own dump (`PCIcon`).

## Command line

| Switch | Effect |
|---|---|
| `--windowed` | Start in a window without changing the settings. |
| `--cemu-ui` | Plain Cemu interface (game list, debugger, graphic pack window) instead of the kiosk mode. |
| `--pce-dev` | Developer mode: separate state in `data_dev` (never touches the player's saves), verbose log, developer bridge. |
| `--extract-icon <game folder> <out.ico>` | Writes the game's icon from a dump and exits (used by the installer for the shortcuts). |
| `--check-game <game folder>` | Exits with what it finds there, as bits: 1 base game, 2 update, 4 the update is 1.5.0, 8 DLC; or with 16 when a disc image is there but not its key (used by the installer; this is how it understands `.wua` archives and disc images). |

## Developer mode

With `--pce-dev` the game opens a line based TCP bridge on `127.0.0.1:28770`. It exists so that changes can be tested
by scripts instead of by hand: inject input, read the interface model, read and write game memory, set logging
breakpoints, take screenshots.

```python
import sys; sys.path.insert(0, 'tools/dev')
import bridge
b = bridge.Bridge()
print(b.cmd('pointer'))      # what the mouse pointer can click right now
print(b.cmd('cursor'))       # the game's menu cursor
b.press('A', 6, 6)           # GamePad button for 6 frames
```

Useful commands (the full list is the `if (c == "...")` chain in `PCDevBridge.cpp`):

| Command | |
|---|---|
| `uistate`, `uitexts`, `uitree <screen>`, `pointer`, `cursor` | Interface model |
| `buttons <mask>`, `stick ...`, `vkeys ...`, `vmouse x y [l] [r]`, `vwheel n` | Input injection |
| `picmap <x> <y> <client width> <client height>` | Where a point of the window lies in the picture (it keeps its shape, so a window of another shape has bars) |
| `rawkey <virtual key> <1 down / 0 up>`, `rawwheel <delta>` | Keyboard and wheel as if they came from the devices (the same code path as real input) |
| `pcmouse <x> <y> [down]`, `pcmouse -1` | The mouse as the PC settings and popups see it (window pixels) |
| `panechain <screen> <text pane>` | Visibility and alpha of a text pane and its parents |
| `nfctouch <file>`, `nfpstate` | Put an amiibo file on the emulated reader; the state of the game's amiibo detection |
| `barriers <0/1>` | Vulkan accurate barriers on / off (for measurements) |
| `read32` / `readf` / `readhex`, `write32` / `writef` | Game memory |
| `logbp <addr> <text with {r3} ...>`, `membp <addr>`, `bpdel <addr>` | Logging breakpoints (written to `log.txt`) |
| `scan ...`, `snap` / `sdiff` | Memory search for values that changed |
| `prof start` / `prof stop <file>`, `perf`, `threads` | Profiling (`tools/dev/prof_resolve.py` resolves a report) |
| `screenshot <file>` | Image of the game window |

`tools/dev/`:

- `run_game.py` starts a developer instance and loads the latest save.
- `bridge.py` is the client used above.
- `rpx.py` disassembles the game executable from your own dump (`set UKING_RPX=...\code\U-King.rpx`; needs
  `capstone`).
- `sendinput.py` and `wincap.py` send real keyboard / mouse input and capture a window.

A typical way to find a hook: set `logbp` on a known function to see who calls it (the log has the link register),
walk up with `rpx.py func`, read the object before and after an input, and prove the idea by writing memory through
the bridge before writing any patch.

## Keeping up with Cemu

The fork branches from Cemu commit `fced55a`. The emulator changes are deliberately few, so a rebase onto a newer
Cemu mostly touches `VulkanRenderer.cpp`, `LatteRenderTarget.cpp`, `MainWindow.cpp` and `CemuApp.cpp`.
